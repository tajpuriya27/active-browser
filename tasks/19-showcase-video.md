## Goal
Add a 31-second showcase video under `media/` and embed it near the top of `README.md`. On https://hexember.github.io/active-browser/ it autoplays muted and loops. On github.com, which strips `<video>`, a poster image stands in and links to the site. The Pages allowlist gains exactly the two media files, and the Swift script that renders the video is kept in the repo so the video can be regenerated.

## Spec (planner)

Scope: two new binary files (`media/showcase.mp4`, `media/showcase-poster.jpg`), one new dev script (`assets/tools/showcase.swift`), and edits to `README.md`, `.github/workflows/pages.yml`, `_config.yml` (comment only), `assets/README.md`, `Project.md`, `CONTRIBUTING.md` and `CHANGELOG.md`. There are no changes under `Sources/` or `Support/`, and none to the `Makefile`, `install.sh`, `ci.yml` or `release.yml`. `media/` is a new top-level path outside `Project.md` §4, so this plan is the guardrail §3 re-plan, and §4 is updated in this PR (item 7).

Planner decisions (the implementer relies on these):
- **Where the media lives.** The media goes in `media/`, as the user asked. `assets/` is in `_config.yml` `exclude:` and must stay there: it holds the app artwork, which is not site content. Jekyll copies `media/*` verbatim as static files, and `jekyll-relative-links` only rewrites `.md` targets, so `src="media/showcase.mp4"` in `index.html` (served at `/active-browser/`) resolves to `/active-browser/media/showcase.mp4`. Commit the files as ordinary git blobs, **not Git LFS**: Pages does not serve LFS objects, and the repo has no `.gitattributes`. At 4.67 MB + 110 KB they are far below GitHub's 50 MB warning.
- **The github.com fallback: Liquid comment trick (accepted).** GitHub strips `<video>` and all its children (the main session verified this), so a poster image linked from the README is the only way to show anything on github.com. The markup is wrapped in `<!-- {% comment %} -->` … `<!-- {% endcomment %} -->`. GitHub renders HTML comments as nothing, so the image between them shows. On Pages, Liquid runs before kramdown and deletes everything from `{% comment %}` to `{% endcomment %}`, including the first comment's `-->` and the second's `<!--`. What remains is one empty `<!--  -->`, which is harmless. I considered and rejected these alternatives:
  - A `github.com/user-attachments` upload. It needs the web UI (a human step), lives outside the repo, and on Pages it renders as a bare link.
  - A poster-only README with no `<video>`. That defeats the request.
  - Two copies of README. That means drift.
- **Where the fallback links.** It links to the **site** (`https://hexember.github.io/active-browser/`), not to `media/showcase.mp4`. On github.com, a relative `.mp4` link opens a blob page that shows "View raw" rather than a player, and the raw URL downloads the file. The site plays the video at the top of the page. Before merge the link opens a site that has no video yet. That's acceptable.
- **Amendment to task 18's "no `{{`/`{%` in published files" rule.** This is a deliberate change. README may contain **exactly one** `{% comment %}` and **exactly one** `{% endcomment %}`, both inside HTML comments. It must contain no `{{` and no other `{%`. The four other published docs stay at zero. Task 18's PAGESSIM Liquid check and its test step 5 are superseded for README by this task's step 3. A new post-build check (item 2) enforces the result: after the build, `index.html` contains no `{%`, `{{` or `comment %}` text, and no fallback `<img>`.
- **Accessibility and motion.** The `<video>` element has `controls`, so anyone can pause it, and an `aria-label` that describes what the video shows. `muted` and `playsinline` are required for autoplay in Safari (including iOS) and Chrome. No `<script>` or `<style>` is used for `prefers-reduced-motion`: GitHub would strip them, and the video has no audio or flashing. `controls` is the mitigation, and this is recorded as a known limitation, not a bug.
- **The script goes in the repo** as `assets/tools/showcase.swift`. The name `render.swift` is already taken by the SVG rasteriser. Because it is under `assets/`, it is never published and never compiled (`Package.swift` only builds `Sources/ActiveBrowser`). It imports only `AppKit` and `AVFoundation`, so it complies with guardrail §1 (zero third-party dependencies). Guardrail §2 (MainActor only, no GCD) governs the app's state, not a one-shot CLI script, so its `DispatchSemaphore` and `Thread.sleep` are acceptable here. That scoping should be stated in the script's header comment.

### Architectural notes and risks
- **Guardrails.** Nothing touches the app, the bundle or the runtime, so every runtime guardrail is n/a. For §1 zero-deps: the script imports only `AppKit`/`AVFoundation`, and no action or gem is added. For the §3 re-plan: `media/` and `assets/tools/showcase.swift` are added to §4 in this PR. For §3 Green Build: `swift build` does not see `assets/`.
- **Liquid fragility.** A future edit that puts a blank line or Markdown between the comment markers still works. Deleting one marker does not: it either shows raw `{% … %}` on github.com or throws a Liquid syntax error on Pages (an unclosed `comment` fails the build, which is the safe failure). Check 5 plus step 3's grep catch both cases.
- **kramdown and raw HTML.** GFM kramdown passes a block-level `<video>` through unchanged, but it may normalise boolean attributes (e.g. `autoplay=""`). Browsers treat both forms the same. Step 10 records the exact emitted tag, and check 5 does not depend on attribute syntax.
- **Autoplay caveats (not bugs).** Safari's Low Power Mode and some data-saver modes block autoplay even for muted video. The poster and play control show instead. The user steps accept this.
- **Repo weight.** Every regenerated video adds about 5 MB to history for good. Replace it only deliberately, and never commit intermediate renders.
- **CDN/MIME.** GitHub Pages serves `.mp4` as `video/mp4` and supports range requests, and the file is faststart, so playback starts before the download finishes. User step 12 checks the header.
- **Binary grep.** The old-domain check `grep -rl 'activebrowser\.app' _site` also scans the mp4 and jpg. A chance match in compressed bytes is effectively impossible, and step 9 confirms none today.
- **Merge order.** This branch is based on `main` (f727d76), with no stacked parent. The merge commit touches `pages.yml`, `README.md` and `media/**`, so it triggers a deploy.
